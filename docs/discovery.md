# Search and AI discovery

Reviewed on 2 September 2026. These files support discovery; they do not guarantee indexing, rankings, or citations. The configured production origin is `https://www.2600th.com`. This document does not confirm a live deployment.

## What we publish

- **`/robots.txt`** keeps the existing open crawl policy and points to the sitemap index. It is maintained in `public/robots.txt`.
- **`/sitemap-index.xml`** and its child sitemap are generated by `@astrojs/sitemap` during the production build. They describe indexable page URLs, not media assets or every file in `public/`.
- **`/sitemap.xml`** is a compatibility index pointing to the same generated child sitemap. The canonical advertised entry remains `/sitemap-index.xml`; the compatibility URL does not create duplicate page records or invented modification dates.
- **`/rss.xml`** contains published notes, generated by `src/pages/rss.xml.ts`.
- **`/llms.txt`** is a short Markdown guide to the portfolio, its projects, and its published notes. `src/pages/llms.txt.ts` generates it using `src/data/llms.ts`. The shared layout links to it with `rel="describedby"`.

The guide is optional. The [llms.txt proposal](https://llmstxt.org/) describes a compact, linked context file, including use on personal sites. It is not a crawler-permission standard. [Google's guidance for AI search features](https://developers.google.com/search/docs/appearance/ai-features) says no special AI text files are required; useful crawlable pages and ordinary search practices remain the foundation.

## Permissions and indexing

No bot-specific restrictions have been added. `User-agent: *` with `Allow: /` keeps the current policy for crawlers that follow robots.txt, including search and training crawlers. Any future choice to block a particular use should be reviewed separately rather than bundled into a discovery update.

The [Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html) is voluntary crawl control, not authentication or a confidentiality boundary. A robots disallow also does not reliably remove a URL from search results; see [Google's robots.txt introduction](https://developers.google.com/search/docs/crawling-indexing/robots/intro). The console archive remains crawlable with `noindex,follow` so a crawler can read that directive. It and the 404 page are absent from the sitemap and guide.

Search and training controls can be separate. For example, [OpenAI documents distinct search and training crawlers](https://developers.openai.com/api/docs/bots). An entry in `llms.txt` does not override robots.txt or give a crawler additional access.

## Content and maintenance

Do not hand-edit `dist/llms.txt` or add a competing `public/llms.txt`. Update the source content and rebuild:

- Identity and current-role copy: `src/data/site.ts`.
- Project titles and summaries: `src/content/work/*.md`.
- Note titles, summaries, publication dates, and draft status: `src/content/notes/*.md`.
- Guide introductions and section structure: `src/data/llms.ts`.

The generator emits an explicit allowlist of public titles, summaries, and canonical links. It does not serialize frontmatter, article bodies, source records, or internal review fields. It normalizes whitespace and escapes Markdown syntax in titles and summaries. Projects use the same selected-systems priority as Work, then historical order. Published notes are newest first. Notes with `draft: true` are excluded, matching the note routes, sitemap and RSS feed. The 19 visible Work records are included. The self-canonical `/work/blocks-inco-ai/` compatibility page is deliberately absent from the guide but remains indexable and present in the sitemap.

The exact `/lab/dwarkesh-jensen/index.html` companion route is registered with the sitemap integration and linked in the guide and Lab. It is a standalone explanatory artifact with its own self-canonical URL, not a second copy of a wrapper page. The interview is credited as its source, not treated as the artifact's author or an endorsement. No duplicate directory alias is registered. The terminal and private drafts remain excluded.

Sitemap `lastmod` comes from `scripts/sitemap-metadata.mjs`: explicit frontmatter `updatedAt`, otherwise the last Git commit date only when the source file is tracked and clean. Uncommitted source, new undated files, index pages and aggregate/template routes omit unknown dates. There is no global build-time date. When substantially revising an article, maintain its real `updatedAt` and visible update date. Original publication dates remain unchanged. This intentionally means different source checkouts can omit dates that are not trustworthy for their working tree.

Person JSON-LD uses the current title and exact LinkedIn, X, GitHub and Substack identities from `src/data/site.ts`. Article JSON-LD matches visible publication/modification dates and the article's unique social image. Work CreativeWork describes Pranshul's case-study writing, with the product as its subject and the visible role as contribution context. It does not assign product ownership or turn a project start year into an article creation date.

Every current work record has a public project route, including records labelled `approval-enhanced`. That field is not a publication filter. The guide reflects the public page summaries; it does not make an additional publication decision. Keep confidential content out of publishable summaries and `public/`, and retain the release review in [deployment.md](deployment.md).

We do not currently add `llms-full.txt`: it would duplicate the site and increase the risk of stale or overly broad exports. `humans.txt` would duplicate the About page. `security.txt` is a separate vulnerability-reporting commitment, not an SEO file; add it only when there is a maintained reporting process and contact, following [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html).

## Verification

Run `npm run verify` before a release. The discovery-specific checks cover:

- Unit tests for draft exclusion, allowlisted fields, Markdown formatting, stable ordering, and input immutability.
- Browser tests for text responses, canonical guide links, published project/note coverage, the shared discovery link, unchanged robots rules, and the archive's noindex directive.
- Build checks for actual guide targets, complete sitemap coverage, canonical URLs, exclusion of noindex pages, duplicate links, and internal metadata leakage.

Astro emits the sitemap only during a build, so `/sitemap-index.xml` is not expected to work in the development server. Use `npm run build`, `npm run test:build`, and `npm run preview` to inspect the complete output. The guide itself is available in development.

After an approved deployment, check `/robots.txt`, `/llms.txt`, `/rss.xml`, `/sitemap-index.xml`, and every referenced child sitemap on the production domain. Confirm 200 responses, the intended content, and appropriate content types. Astro's endpoint returns `text/plain; charset=utf-8` locally, but the static host controls deployed response headers. A local pass does not prove live headers or crawler adoption. See [Astro's static endpoint documentation](https://docs.astro.build/en/guides/endpoints/) and [Google's sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).
